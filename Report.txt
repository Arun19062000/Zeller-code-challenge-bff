1. EXECUTIVE SUMMARY & ARCHITECTURAL BLUEPRINT
--------------------------------------------------------------------------------
Executing a synchronous Materialized View Refresh inside an ingestion Lambda 
function operating at 30 TPS causes severe pipeline failure. At 30 TPS over 2 
years of data, binding database view updates to transactional message consumption 
causes Lambda execution timeouts, exponential SQS backlogs, database lock 
contention, and SLA breaches.

To strictly meet your 3-minute Service Level Agreement (SLA) for near real-time 
Power BI consumption, decoupling write operations from view refreshes using an 
EventBridge-orchestrated Refresher Lambda alongside a Hot/Cold View Architecture 
is required.

2. FAILURE ANALYSIS: SYNCHRONOUS REFRESH INSIDE LOADER LAMBDA
--------------------------------------------------------------------------------
Executing `REFRESH MATERIALIZED VIEW` inside the ingestion Lambda breaks pipeline 
mechanics at 30 TPS:

A. Ingestion Math vs. Execution Duration:
   - Incoming Ingestion Rate: 30 TPS = 2,700 events every 90 seconds.
   - Batch Capacity: SQS payloads max out at 6 MB; BatchSize caps at 1,000 records.
   - Database Query Latency: Calculating window functions (LAST_VALUE IGNORE NULLS) 
     across millions of historical rows takes 45 to 90+ seconds per view refresh.
   - The Throughput Gap: At ~60 seconds per refresh execution, a single worker 
     handles ~16.6 TPS maximum. The remaining 13.4 TPS accumulates in SQS continuously.

B. The Fallacy of Setting Concurrency = 1:
   - Restricting Loader Lambda concurrency to 1 to force sequential executions 
     creates Line-of-Head Blocking.
   - Queue Saturation: 30 TPS generates 2,592,000 events daily. At 1,000 records 
     per execution taking 60 seconds, Concurrency = 1 processes only 1,440,000 
     records daily, leaving a backlog of >1 million unprocessed messages per day.
   - Data Expiry Hazard: Messages exceed SQS MessageRetentionPeriod (e.g., 4 days) 
     and drop silently into Dead Letter Queues (DLQ) or expire, causing permanent 
     data loss.

C. Database Resource Exhaustion & Lock Contention:
   - If Lambda concurrency is unconstrained, dozens of concurrent Lambda executions 
     fire overlapping REFRESH MATERIALIZED VIEW statements simultaneously.
   - Redshift Workload Management (WLM) queues fill immediately, triggering "Too many 
     database connections" errors, High Disk I/O contention, and transaction lock waiting.
   - Cost Inefficiencies: Lambda bills based on GB-seconds. Spending 90% of execution 
     time idling while waiting for database queries drastically inflates AWS costs.

3. AMAZON REDSHIFT PHYSICAL DATA LAYOUT OPTIMIZATION
--------------------------------------------------------------------------------
Amazon Redshift does not use traditional B-tree indexes. High performance depends 
on Data Distribution Styles, Sort Keys, and Zone Map metadata.

A. Distribution Key (DISTKEY (trnid)):
   - Co-locates all historical events belonging to a specific transaction ID (trnid) 
     onto the same physical Redshift compute node slices.
   - Evaluates `PARTITION BY trnid` window functions entirely within local slice 
     memory, eliminating network data reshuffling (BROADCAST/HASH JOIN steps) across 
     cluster nodes.

B. Compound Sort Key (COMPOUND SORTKEY (last_modified, trnid)):
   - Orders physical data blocks on disk sequentially by timestamp first, then 
     transaction ID.
   - Zone Map Block Skipping: Redshift maintains in-memory metadata (Zone Maps) 
     tracking the Minimum and Maximum `last_modified` values for every 1 MB disk block.
   - Query Pruning: When a query contains `WHERE last_modified >= DATEADD(day, -30, CURRENT_DATE)`, 
     Redshift reads only the relevant active blocks and skips 95%+ of historical 1 MB 
     blocks on disk.

C. Redshift Delta Limit with Window Functions:
   - Redshift supports Incremental Materialized Views (updating only changed rows) 
     for standard aggregations (SUM, COUNT).
   - Technical Limitation: Redshift CANNOT perform incremental refreshes on views 
     containing OVER() window functions (LAST_VALUE, LAG, LEAD). Redshift defaults to 
     a Full Query Recompute.
   - Workaround: By pairing a Full Recompute view query with an explicit date-bounding 
     predicate (WHERE last_modified >= ...), Zone Maps restrict the scope of the full 
     scan to active storage blocks, reducing execution times from minutes to seconds.

4. DEEP-DIVE: HOT/COLD VIEW ARCHITECTURE & DDLS
--------------------------------------------------------------------------------

-- DDL 1: Master Raw Table
CREATE TABLE master_table (
    trnid VARCHAR(64) NOT NULL,
    last_modified TIMESTAMP NOT NULL,
    val VARCHAR(256),
    created_at TIMESTAMP DEFAULT SYSDATE
)
DISTSTYLE KEY
DISTKEY (trnid)
COMPOUND SORTKEY (last_modified, trnid);

-- DDL 2: Hot Materialized View (Active 30-Day Bounded Window)
CREATE MATERIALIZED VIEW mv_master_hot AS
SELECT 
    trnid,
    last_modified,
    LAST_VALUE(val IGNORE NULLS) OVER (
        PARTITION BY trnid 
        ORDER BY last_modified
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS filled_val
FROM master_table
WHERE last_modified >= DATEADD(day, -30, CURRENT_DATE);

-- DDL 3: Cold Materialized View (Historical Frozen Data)
CREATE MATERIALIZED VIEW mv_master_cold AS
SELECT 
    trnid,
    last_modified,
    LAST_VALUE(val IGNORE NULLS) OVER (
        PARTITION BY trnid 
        ORDER BY last_modified
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS filled_val
FROM master_table
WHERE last_modified < DATEADD(day, -30, CURRENT_DATE);

-- DDL 4: Unified Standard View (Power BI Consumption Layer)
CREATE VIEW master_view_2years AS
SELECT trnid, last_modified, filled_val FROM mv_master_hot
UNION ALL
SELECT trnid, last_modified, filled_val FROM mv_master_cold;

5. PRODUCTION CONFIGURATION CHECKLIST
--------------------------------------------------------------------------------

1. SQS Queue & Loader Lambda Tuning:
   - SQS `MaximumBatchingWindowInSeconds`: Set to `30 seconds`. Ensures incoming 
     messages do not sit idling in SQS.
   - SQS `BatchSize`: Set to `500 - 1000 records`. Keeps message payload size safely 
     under the 6 MB Lambda limit.
   - Loader Lambda Concurrency: Set Reserved Concurrency to `5 - 10`. Absorbs micro-bursts 
     while keeping DB connections bounded.
   - Loader Lambda Execution Focus: Fast bulk staging INSERT commands into master_table 
     only. Completes in < 1.0 second.

2. EventBridge & Refresher Lambda Orchestration:
   - EventBridge Trigger Schedule: Set to `rate(2 minutes)`.
   - Refresher Lambda Execution: Calls `REFRESH MATERIALIZED VIEW mv_master_hot;`.
   - Refresher Lambda Timeout: Set to `3 minutes`.
   - Cold Refresher Schedule: Set an EventBridge rule to execute 
     `REFRESH MATERIALIZED VIEW mv_master_cold;` once weekly (e.g., Sunday at 2:00 AM IST).

3. Power BI DirectQuery Optimization:
   - Direct Connection: Connect Power BI directly to `master_view_2years`.
   - Predicate Pushdown: Ensure Power BI reports pass default filters 
     (WHERE last_modified >= CURRENT_DATE). Redshift prunes mv_master_cold entirely 
     for real-time dashboards.
